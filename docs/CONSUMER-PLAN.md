# Per-field consumer implementation plan

Scopes the defined-but-(under)used fields flagged in `CONFORMANCE.md`. Each
entry is grounded in the actual bridge/scanner patterns this CLI already uses
(`internal/bridge/<name>/`, `internal/scanners/`). No code is implemented here
— this is the per-field design contract to review before building.

Conventions referenced below:

- **Renderer** (derive-only) bridge pattern:
  `internal/bridge/{funding,security,coc}/{view.go,bridge.go,register.go}` implementing `core.Renderer`; multi-file
  `Output{Files: map[relpath][]byte}`; blank-imported from `internal/cmd/bridge.go`; `make`-style registration in
  `init()` via `bridge.Register(Bridge{})`.
- **Syncer** (round-trip) mapper pattern: `internal/bridge/cff/mapper.go`
  `FieldMapper{ExtKey, PFKey, ToPF, FromPF}`.
- **Multi-target snippet Renderer**: `internal/bridge/ignore/` with the
  `targets` table in `register.go` and `overrideFor` in `bridge.go`.

## `requirements.browsers` — `.browserslistrc` renderer

| Aspect                 | Detail                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
|------------------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| What "consuming" means | Emit a `.browserslistrc` file: one query line per `requirements.browsers` entry (the field is already `[]string` of browserslist queries, e.g. `last 2 versions`, `> 0.5%`, `not dead`). Pf is authoritative; derive-only (no read-back — the schema description in `internal/validate/embedded/v1.json` already promises browserslistrc generation).                                                                                                     |
| Command / package      | New `internal/bridge/browserslist/` Renderer. Surfaced as `pf-bridge browserslist` (Renderer → auto-resolves to `to`).                                                                                                                                                                                                                                                                                                                                    |
| Files to touch         | `internal/bridge/browserslist/{view.go,bridge.go,register.go}` (mirror `bridge/funding/`); `internal/cmd/bridge.go` (blank import). Optional `templates/.browserslistrc.tmpl` or direct byte emit (queries are line-oriented — direct emit like the ignore assembler is simpler than a template). `Policy{Marker: true}` using `core.Marker` (`# pf-cli-managed: yes`) so hand-edits are protected. `RequiredFields` → `requirements.browsers` non-empty. |
| Effort                 | **S** — one short Renderer, no SPDX/template machinery, field is already a plain string slice.                                                                                                                                                                                                                                                                                                                                                            |
| Open questions         | (1) Marker vs. ScaffoldOnce — `.browserslistrc` is data-only so `Marker` fits the `.gitignore`/`FUNDING.yml` precedent. (2) Should an empty/comment-only browsers list suppress the file (no-op) like the ignore `hasContent` filter? (3) `package.json` already carries a `browserslist` key — out of scope here, but a future npm syncer mapper could mirror `requirements.browsers` ↔ `browserslist`; flag so the two don’t diverge.                   |

## `license.covers` + `license.file` — REUSE relationship

| Aspect                 | Detail                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
|------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| What "consuming" means | Honor the spec §4.4 `license` table + §"Scope: covers". (a) `license.file` (string or string-sequence): when set, the LICENSE renderer writes to those path(s) instead of the default `LICENSE`, and for a sequence emits the REUSE-style fan-out (`LICENSE-MIT`, `LICENSE-APACHE`, or `LICENSES/*.txt`) keyed by the declared paths rather than the synthesised `LICENSE-<id>` names it invents today (`bridge/license/bridge.go:88-94`). (b) `license.covers`: `additions` is a signal — emit a decision-trace line and (optionally) a banner/NOTICE hint that `license.spdx` is NOT authoritative for the full tree (spec §4.4 "Consumers ... MUST treat covers: additions as a signal"). Default `project` = current behavior. |
| Command / package      | Existing `internal/bridge/license/` Renderer (extend, do not add a bridge).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| Files to touch         | `internal/bridge/license/bridge.go` (`FullPath` + `Render`: resolve output path(s) from `pf.License.File`; branch on `pf.License.Covers`); `internal/bridge/license/helpers.go` (path-list normalisation: single string vs sequence — note `License.File` current Go type must be checked, may need a string-or-list shape); `internal/bridge/license/view.go` if a NOTICE/boundary line is templated; `license_test.go`.                                                                                                                                                                                                                                                                                                          |
| Effort                 | **M** — touches multi-file Output keying and the path rules in spec §8; `covers: additions` semantics (what exactly to emit) need a product decision.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| Open questions         | (1) Does `license.file` currently parse as `string` or `[]string` in `types.go`? Spec allows both — confirm the round-trip shape before wiring. (2) For `covers: additions`, is the deliverable just a decision-trace log, or also a generated `NOTICE`/boundary note? (3) Path-escape/`..` validation per spec §8 path rules. (4) Interaction with compound-SPDX fan-out — if both `file` sequence AND compound expr are present, which names win?                                                                                                                                                                                                                                                                                |

## `identity.released` + `identity.modified` — dates in CITATION.cff

| Aspect                 | Detail                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
|------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| What "consuming" means | `identity.released` is **already consumed** by the CFF syncer (`bridge/cff/mapper.go:124` maps it ↔ `date-released`) — CONFORMANCE.md’s ROUND-TRIP-ONLY label is stale for this one; the plan item is to (a) correct the audit and (b) close the symmetric gaps: `identity.modified` has NO cff mapper and `cff.Document` has no `date-modified`/`DateModified` field (`document.go:16` only has `DateReleased`). CFF 1.2.0 has no native `date-modified`, so `identity.modified` would need a home (skip in cff, or surface elsewhere). Neither `released` nor `modified` is auto-populated — only `identity.created` is (Git root-commit, `scanners/git/scanner.go:112`); a scanner could set `modified` from the latest commit date and `released` from the newest tag. |
| Command / package      | `internal/bridge/cff/` (mapper + document) for `released`; `internal/scanners/git/` for auto-population of `modified`/`released`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| Files to touch         | `internal/scanners/git/scanner.go` (populate `p.Modified` from HEAD commit date, `p.Released` from latest SemVer tag, mirroring the existing `Created` population). For cff `date-modified`: only if a target schema is chosen — otherwise document the deliberate omission. `internal/source/cff.go` if init-time detection should seed dates. Tests in the respective `_test.go`.                                                                                                                                                                                                                                                                                                                                                                                        |
| Effort                 | **S** (Git scanner populate) / **M** (if a new external sink for `modified` is added).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| Open questions         | (1) Confirm + fix CONFORMANCE.md: `identity.released` is CONSUMED via cff. (2) Where does `identity.modified` go? CFF lacks `date-modified`; candidates: drop, or a future Schema.org `dateModified` export. (3) `released` from "latest tag" needs a tag→SemVer policy; "newest by committer date" vs "highest SemVer" is a decision. (4) Should auto-population overwrite an explicit pf value, or gap-fill only (the cff mapper’s `force` semantics already model gap-fill)?                                                                                                                                                                                                                                                                                            |

## `people[].alias` — emit in a bridge

| Aspect                 | Detail                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
|------------------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| What "consuming" means | `Alias` is merged in `people.go:178` (round-trips) but no bridge emits it. Define a concrete sink: (a) CODEOWNERS — when a person has an `alias` that is a forge handle (`@octocat`), prefer it over the email when rendering owner tokens (`bridge/codeowners/`). (b) CFF — CFF has no `alias` field, so no sink there. (c) `package.json`/`composer` author strings — npm `author` is `Name <email> (url)`; `alias` has no slot. The realistic single consumer is CODEOWNERS handle resolution. |
| Command / package      | `internal/bridge/codeowners/` (mapper / owner-token resolution).                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| Files to touch         | `internal/bridge/codeowners/mapper.go` (owner-token derivation: use `alias` when it looks like `@handle`); possibly `internal/projectfile/people.go` (a `ForgeHandle(p)` helper). `codeowners` mapper tests.                                                                                                                                                                                                                                                                                      |
| Effort                 | **S** — single resolution rule in one mapper.                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| Open questions         | (1) Is `alias` semantically a forge handle, a nickname, or a display alias? The spec field semantics gate which bridge consumes it — confirm before wiring. (2) If `alias` is freeform (not a handle), CODEOWNERS is the wrong sink and the honest answer may be "stays round-trip-only until a use case exists" — surface that option rather than force a consumer.                                                                                                                              |

## `org.projectfile.ignores` — wire `.npmignore` / `.trivyignore` overrides

| Aspect                 | Detail                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
|------------------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| What "consuming" means | `bridge/ignore/register.go` registers four targets (git/docker/npm/trivy) but `IgnoresExtension` (`types.go:165-167`) only has typed `Git`/`Docker` override slots, so `overrideFor` (`bridge.go:151`) returns `nil` for npm/trivy — those two cannot carry per-target `include`/`exclude`. Consuming = add the missing slots so all four targets honor `[org.projectfile.ignores.<extKey>].include/exclude` symmetrically.                                     |
| Command / package      | `internal/projectfile/` (extension struct + helper) and `internal/bridge/ignore/` (switch arm).                                                                                                                                                                                                                                                                                                                                                                 |
| Files to touch         | `internal/projectfile/types.go` (add `Npm *IgnoreTargetOverride` and `Trivy *IgnoreTargetOverride` to `IgnoresExtension`); `internal/projectfile/helpers.go` (`GetIgnoresExtension` populates the two new fields); `internal/bridge/ignore/bridge.go` (`overrideFor` switch: add `case "npm"` / `case "trivy"`); update the `overrideFor` doc comment (currently says "only Git and Docker"). Tests for npm/trivy override application.                         |
| Effort                 | **S** — purely additive, follows the documented "add an ignore-file target" recipe (AGENTS.md) in reverse; the snippet table already lists npm/trivy.                                                                                                                                                                                                                                                                                                           |
| Open questions         | (1) Generalise to a `map[string]*IgnoreTargetOverride` keyed by extKey instead of named fields? The `overrideFor` comment already calls a map "a follow-up" — a map removes the per-target boilerplate but diverges from the explicit-field convention the struct uses today (OCD-consistency lens: explicit named fields match `Git`/`Docker`). (2) Spec shape `spec/shapes/org.projectfile.ignores.toml` must enumerate npm/trivy sub-tables to stay in sync. |

## Effort summary

| Field                                              | Effort |
|----------------------------------------------------|--------|
| `requirements.browsers` (.browserslistrc renderer) | S      |
| `license.covers` + `license.file` (REUSE)          | M      |
| `identity.released` + `identity.modified` (dates)  | S–M    |
| `people[].alias`                                   | S      |
| `org.projectfile.ignores` npm/trivy overrides      | S      |

Total: roughly **4×S + 1–2×M**. The two genuinely-scoped (M) risks are
`license.file`/`covers` path-and-corpus semantics and a possible new external
sink for `identity.modified`; everything else is additive within an existing
bridge/scanner pattern.
